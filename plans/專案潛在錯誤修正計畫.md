# 專案潛在錯誤修正計畫

## 一、目的

修正目前專案中已確認或可重現的入口、資料驗證、檔案儲存及 Google Workspace 同步問題，並補足相關自動測試，避免錯誤資料寫入 CSV、JSON 或 Google Sheets。

本計畫不包含功能擴充、UI 改版、OCR prompt 調整或模型更換。

## 二、最終決策

以下決策已確認，實作時不再另行選擇方案：

1. 全專案統一使用 `src.*` 絕對匯入，以 `uv run python -m src...` 作為標準啟動方式。
2. `DocumentProcessor` 接受可選的 `prompts_path`；未提供時使用 `config.settings.PROMPTS_PATH`。
3. 必填欄位不得缺少、為 `None`、空字串或只有空白。
4. `key_points` 接受任意數量的 `list[str]` 或逗號分隔字串，但不得為空、錯誤型別或包含非字串元素。
5. 公文日期超過 90 天時判定驗證失敗。
6. CSV 遇到單筆結構錯誤時跳過該筆，其他資料繼續寫入，並回傳錯誤原因。
7. Drive 任一檔案上傳失敗時，取消該批次的 Sheets 同步。
8. Drive 覆寫失敗時直接標記失敗，不改為新增版本；既有檔案及 ID 保留。
9. 使用者取消上傳後停止啟動新請求，等待進行中的請求安全結束，且不得執行 Sheets 同步。
10. Google 認證失敗不阻止本地功能；使用雲端功能時才提示未認證。
11. `LocalStorage` 有傳入 `output_dir` 時優先使用；未傳入才使用設定檔。
12. 移除 `StorageBackend` singleton，由 controller 明確持有及傳遞實例。
13. CSV 批次寫入回傳結構化統計及逐筆錯誤。
14. 日誌由 CLI／GUI 入口顯式初始化；一般模組匯入不得修改 handler。
15. 本次不修改 QML，相關警告另案處理。
16. 驗證失敗的公文仍寫入主要 CSV，保留 `is_valid=False`、`error_code`、可取得欄位及處理時間。
17. Google Drive／Sheets 自動測試全部使用 mock；發布前另以測試帳號執行手動整合測試。

## 五、第二階段：強化資料驗證

涉及檔案：

- `src/domain/validator.py`
- `src/infrastructure/local_storage.py`
- `tests/`

### 5.1 必填欄位規則

以下欄位不得缺少、為 `None`、空字串、只有空白或為錯誤型別：

- `doc_date`
- `doc_category`
- `doc_number`
- `doc_from`
- `case_officer`
- `related_class`
- `key_points`

### 5.2 `key_points` 型別與內容

允許的輸入型別：

- `list[str]`
- 逗號分隔字串，轉換成 `list[str]`

必須拒絕：

- 整數
- dict
- bool
- 含非字串元素的 list
- `None`
- 空 list
- 空字串或只含分隔符號、空白的字串

不限制關鍵字數量，但轉換後至少要有一個非空字串。

### 5.3 CSV 寫入防禦

`LocalStorage.append_batch()` 不應直接以 `csv_data["field"]` 假設欄位一定存在。應採以下策略之一：

- 寫入前驗證完整 schema。
- 使用明確的資料物件。
- 對缺失欄位回報結構化錯誤並跳過該筆。

不得因單筆資料缺欄位而中斷整批 CSV 寫入。結構無法安全寫入的
資料應跳過，並加入批次結果的 `errors`。

### 5.4 日期規則

日期格式錯誤或與處理日期相差超過 `DATE_VALIDATION_DAYS` 時，均判定
驗證失敗。日誌可記錄 WARNING，但不得將該筆視為有效資料。

### 5.5 驗證失敗資料的 CSV 行為

可安全正規化的驗證失敗資料仍寫入主要 CSV，內容至少包含：

- `is_valid=False`
- `error_code`
- 可取得的公文欄位
- `processed_time`

只有資料結構無法安全轉換或實際 I/O 寫入失敗時才跳過。

### 5.6 第二階段測試

- 缺少任一必填 Key 時失敗。
- 必填欄位為 `None` 時失敗。
- `key_points` 為整數、dict、bool 時失敗。
- `key_points` 為合法字串陣列時成功。
- 逗號分隔字串能正確轉換。
- list 含非字串元素時失敗。
- CSV 缺欄位時不會拋出未處理的 `KeyError`。
- 90 天邊界成功，超過邊界時驗證失敗。
- 驗證失敗但可安全正規化的資料會寫入失敗列。
- 無法安全寫入的單筆資料被跳過，其他筆仍繼續。

## 六、第三階段：確保 Drive 與 Sheets 資料一致

涉及檔案：

- `src/infrastructure/google_workspace/drive_service.py`
- `src/infrastructure/data_storage.py`
- `src/ui/doc_controller.py`

### 6.1 上傳結果模型

將上傳結果統一為結構化資料，例如：

```python
{
    "name": "document.jpg",
    "success": True,
    "file_id": "...",
    "action": "create",
    "error_code": "",
    "message": ""
}
```

不得以 `None` 表示所有失敗情況，也不得將覆寫失敗回傳為成功。

### 6.2 覆寫失敗處理

Drive update 失敗時：

1. 回傳失敗結果。
2. 不將既有 ID 當作本次成功證明。
3. 保留既有 `drive_file_id`，但標示內容未更新。
4. UI 顯示失敗檔名及原因。

### 6.3 Sheets 同步條件

只有整批 Drive 上傳全部成功時才執行 Sheets 同步。明確選擇 SKIP 且
已有有效既存 Drive ID 的項目視為成功。

若任一必要圖片新增或覆寫失敗：

- 取消整批 Sheets 同步。
- 保留已成功上傳的 Drive 檔案。
- 回報成功、失敗及未同步數量。
- 不得寫入連結為空或內容版本不正確的 Sheets 資料。

### 6.4 Google 測試策略

- 自動測試使用 mock，不依賴實際 Google 憑證、網路或雲端資料。
- 發布前使用獨立測試帳號及測試資料夾執行手動整合測試。
- 手動測試結果不得寫入正式 Drive 或正式試算表。

### 6.5 第三階段測試

- 新增上傳成功後才同步 Sheets。
- 覆寫成功時保留正確 ID。
- 覆寫失敗不會被計為成功。
- SKIP 且有既有 ID 時可同步。
- 任一 Drive 項目失敗時，整批 Sheets 同步不會執行。
- 部分上傳成功時，Drive 檔案保留且統計與 UI 訊息正確。

## 七、第四階段：背景取消與認證狀態

### 7.1 可取消的上傳流程

涉及檔案：

- `src/ui/doc_controller.py`
- `src/infrastructure/data_storage.py`
- `src/infrastructure/google_workspace/drive_service.py`

修改內容：

1. 建立可跨 QThread、async task 與同步 upload worker 使用的 cancellation token。
2. 每個檔案上傳前檢查取消狀態。
3. 取消後不再啟動新的 Drive 請求。
4. 取消後不得繼續同步 Sheets。
5. 對已送出的無法取消請求，等待其安全結束並回報實際狀態。

### 7.2 Google 認證物件完整初始化

涉及檔案：

- `src/infrastructure/google_workspace/__init__.py`

所有屬性應在進入可能失敗的認證流程前初始化：

- `_cred_general`
- `_cred_user`
- `_token_path`
- `_client_secret_path`
- `_project_id`
- `_service_account_email`
- `_auth_success`

未認證時，service property 應一致拋出 `UnauthenticatedError`，避免不明確的 `AttributeError`。

認證失敗不得阻止 GUI 啟動或本地新增、分析、CSV、JSON 功能。只有使用
Drive 或 Sheets 時才顯示未認證錯誤。

### 7.3 第四階段測試

- 取消後不再開始新上傳。
- 取消後不執行 Sheets 同步。
- UI 顯示取消，但不誤報全部完成。
- 缺少 service account 檔案時物件仍保持可查詢狀態。
- 未認證時 service property 回傳一致錯誤。
- OAuth token 過期與更新失敗有明確結果。

## 八、第五階段：儲存與日誌穩定性

### 8.1 修正 `LocalStorage(output_dir)`

涉及檔案：

- `src/infrastructure/local_storage.py`

要求：

- 有傳入 `output_dir` 時必須優先使用。
- 未傳入時才使用設定檔預設值。
- 不再依賴 ImportError 決定路徑。
- 測試使用暫存資料夾，不寫入正式輸出。

### 8.2 移除 StorageBackend singleton

涉及檔案：

- `src/infrastructure/data_storage.py`

移除 `__new__` singleton 與 `_initialized` 短路邏輯，由 `DocController`
建立並持有 storage 實例。需要共享 storage 的服務應由建構子或方法參數
明確接收，不再依賴全域實例。

### 8.3 修正批次寫入統計

`append_batch()` 應分別回傳：

```python
{
    "written": 10,
    "valid": 8,
    "invalid": 2,
    "skipped": 0,
    "errors": []
}
```

不得將無效資料也累加到名為 `success_count` 的數值中。

### 8.4 由入口初始化 logger

涉及檔案：

- `src/infrastructure/logger.py`

要求：

- `logger.py` 提供明確的初始化函數。
- CLI 與 GUI 入口在啟動時呼叫初始化函數。
- 一般模組匯入不得建立、清除或修改 handler。
- 初始化函數必須具備冪等性，重複呼叫不會產生重複日誌。
- 保留 app log、error log 與 console 等既有輸出需求。

### 8.5 第五階段測試

- 自訂 `output_dir` 確實生效。
- 測試不寫入正式 `data/output_results`。
- 不同 storage 實例不互相污染。
- 寫入統計能區分有效、無效及寫入失敗。
- 匯入 logger 不會刪除外部 handler。
- 重複匯入不會產生重複日誌。

## 十、整體驗收標準

- CLI、GUI launcher 與模組入口可從專案根目錄啟動。
- 不再需要手動修改 `sys.path`。
- 必填欄位及 `key_points` 非法資料不會通過驗證。
- 單筆錯誤不會使整批 CSV 寫入意外中斷。
- Drive 上傳結果與 Sheets 同步資料一致。
- 覆寫失敗、部分成功及取消都有正確狀態。
- 自訂輸出路徑與測試隔離正常。
- Google 認證失敗不會產生部分初始化的物件錯誤。
- Logger 不破壞外部 root logger 設定。
- Python 全專案編譯通過。
- 所有單元測試與整合測試通過。
- 本次修改不新增 QML lint 警告；既有 QML 警告留待後續計畫處理。

## 十一、建議執行方式

每一階段應獨立完成：

1. 先新增能重現問題的失敗測試。
2. 實作最小範圍修正。
3. 執行該階段測試。
4. 執行完整回歸測試。
5. 確認日誌、CSV、JSON 或雲端資料沒有非預期副作用。

不建議一次修改所有階段，以免匯入、儲存、執行緒及雲端同步問題互相影響，增加回歸定位難度。
